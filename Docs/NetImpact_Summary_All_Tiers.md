# NetImpact — สรุปผลการทดลองทั้งโครงการ (Baseline ถึง Tier 9)

*เอกสารนี้สรุปเฉพาะ "ผลลัพธ์" ของแต่ละ Tier เท่านั้น ไม่มีลำดับเหตุการณ์ว่าใครทำอะไรตอนไหน ตัวเลขทุกตัวอ้างอิงจากเอกสารชุด `Paper/NetImpact.md/Current/` ซึ่งเป็นสถานะล่าสุดและสุดท้ายของโครงการ*

---

## ระบบที่วัด

ระบบคือ AutoGen multi-agent workflow สามบทบาท (Planner, Worker, Reviewer) ที่รันในโปรเซสเดียว คุยกันในหน่วยความจำ ไม่มีข้อความระหว่าง agent ที่ผ่านเครือข่ายจริง สิ่งที่ผ่านเครือข่ายมีอย่างเดียวคือคำขอ inference จาก Worker/Reviewer (และบางครั้ง Planner) ไปยัง Ollama model server บนโฮสต์ ซึ่งถูกรบกวนด้วย Linux `tc`/`netem` — ควบคุม delay, packet loss, jitter, และ bandwidth cap — โดย **ใช้งานที่ egress เท่านั้นเป็นค่าเริ่มต้นของโครงการ** (ยกเว้น Tier 8 item 4 ที่ทดสอบ bidirectional แยกต่างหาก)

---

## Baseline (1,544 trials, 4 phases, model `qwen3:8b`)

- **Packet loss คือแกนที่ทำให้ระบบล้มเหลว ส่วน delay และ jitter (ทดสอบทีละแกน) ไม่แสดงผลชัดเจน** — delay ถึง 1,000 ms และ jitter ถึง 75 ms completion อยู่ที่ 20/20 แทบทุกระดับ ขณะที่ 75% configured loss คือจุดที่ระบบล้มเหลวชัดเจน (timeout, connection error, retry หมด)
- **จุดเดี่ยวอาจดูปลอดภัย แต่จุดรวมหลายปัจจัยมักไม่ปลอดภัย (เชิงพรรณนา)** — จุดรวมที่ล้มเหลวเกือบทั้งหมดมี loss ≥ 50% และจุดที่ล้มเหลวรุนแรงทั้ง 7 จุดมี loss = 75% ทุกจุด (ไม่ผ่านนัยสำคัญทางสถิติ ดูหัวข้อสถิติด้านล่าง)
- **งาน research-summary เป็น task ที่ยากโดยตัวมันเอง ไม่ใช่ตัวบ่งชี้ความไวต่อเครือข่าย** — คะแนน rubric ต่ำแม้ที่ zero impairment (ANOVA F = 20.4, p < 0.001, Cohen's d = 2.00)
- **ข้อสังเกตที่ 4 ถูกถอนออก**: เคยเชื่อว่าช่องว่างระหว่างคะแนน Reviewer กับ rubric กว้างขึ้นเมื่อมี impairment (0.360 → 0.913) แต่เมื่อคำนวณบน trial ชุดเดียวกันทั้งสองฝั่ง ช่องว่างจริงคือ 0.360 → 0.305 (ไม่กว้างขึ้น) ตัวเลข 0.913 เดิมเกิดจากการเทียบ mean บนฐาน trial ที่ไม่เท่ากัน
- 96.4% ของ trial (1,489/1,544) จบในรอบเดียว (Planner→Worker→Reviewer) เท่านั้น

**การวิเคราะห์เชิงสถิติเพิ่มเติมบนชุดข้อมูลเดียวกัน:** loss มีความสัมพันธ์แบบ monotonic กับ elapsed time (Spearman ρ = 0.38, p < 0.001) ส่วน delay/jitter ไม่พบความสัมพันธ์ที่ชัดเจน; logistic regression ที่รวมทั้งสามแกนพบว่า loss เพียงแกนเดียวอธิบาย pseudo-R² ได้เกือบทั้งหมด (0.474 จาก 0.478 ของโมเดลเต็ม); ข้อกล่าวอ้างเดิมที่ว่า "ปัจจัยรวมกันอันตรายกว่าปัจจัยเดี่ยว (interaction effect)" **ไม่ผ่านนัยสำคัญทางสถิติ** (Fisher's exact p = 0.176, OR = 2.49) — ต้องถอยไปเป็นข้อสังเกตเชิงพรรณนาเท่านั้น

## Tier 1 — Precision Re-measurement (320 trials)

- **แคบขอบเขต degradation region ของ packet loss จาก 50-75% (กว้าง) เหลือ 70-75%**: completion คงที่ 20/20 ถึง 65%, ตก 19/20 ที่ 70%, และ 16/20 ที่ 75% mean error ต่อ trial เริ่มไต่ขึ้นตั้งแต่ 65% ก่อนที่ completion จะเริ่มตก (Clopper-Pearson 95% CI ทับซ้อนกันมากในช่วงนี้ จึงบอกได้แค่ "ช่วง" ไม่ใช่ "จุดขีดแบ่งที่แม่นยำ")
- **จุดผิดปกติที่ delay=250ms ถูกยืนยันว่าเป็นสัญญาณรบกวนธรรมดา**: ทดสอบซ้ำ 15 ครั้งได้ 60/60 (รวมของเดิม 79/80)
- **การไม่พบผลกระทบของ delay/jitter ยังคงอยู่แม้ขยายช่วงถึงจุดสุดขั้ว** — delay ถึง 3,000 ms และ jitter ถึง 200 ms ยังไม่พบ degradation ชัดเจน
- **สถานะปัจจุบัน**: ภูมิภาค 70-75% นี้ **จำเพาะกับช่วงเวลาที่วัด** — การวัดในช่วงเวลาหลัง (Tier 8 §6) พบว่า 75% configured loss ไม่ทำให้ completion ตกอีกต่อไปในสภาพแวดล้อมที่ inference เร็วขึ้นราว 2 เท่า และ Tier 9 พบว่าจุดวิกฤตของสภาพแวดล้อมใหม่คือ 80% ไม่ใช่การเขียนทับผลเดิม แต่ทั้งสองผลลัพธ์ถูกต้องเฉพาะช่วงเวลาที่วัด

## Tier 2 — แกนที่ 4 (Bandwidth) + โหมด Multi-round เข้มงวด

**ส่วนที่ 1 — Bandwidth:**
- **ไม่พบ degradation ชัดเจนแม้ที่ bandwidth ต่ำสุดที่ทดสอบ (50 kbit/s)** — completion คงที่ 20/20 ทุกระดับตั้งแต่ 2,000 ถึง 50 kbit/s รวมทั้งเมื่อรวมกับ loss 10/30/50%
- **ข้อจำกัดสำคัญ**: token-bucket filter อยู่ที่ egress เท่านั้น จำกัดแค่ request ขาออก (payload เล็ก) ไม่ใช่ response ขาเข้า (payload ใหญ่กว่ามาก) — ผลนี้จึงไม่ใช่หลักฐานว่า bidirectional cap ที่ระดับเดียวกันจะให้ผลเหมือนกัน (ปิดข้อจำกัดนี้เฉพาะจุด 50 kbit/s แล้วบางส่วนใน Tier 8 item 4)

**ส่วนที่ 2 — โหมด task ยากขึ้น + Reviewer เข้มงวด (80 trials):**
- การออกแบบนี้ **เพิ่มอัตราการ revision cycle ได้จริง** (29/80 = 36.3% เทียบกับ 1.75% ในชุดเดิม) แต่ไม่ได้บังคับให้เกิด revision (51/80 = 63.8% ไม่ได้รับ Reviewer rejection เลย — 50 ในจำนวนนี้จบในรอบเดียว 3 ข้อความ ส่วนอีก 1 รอบวิ่งไปถึง 6 ข้อความจาก retry ไม่ใช่จาก rejection)
- completion โดยรวมต่ำกว่าโหมดปกติ (67/80) โดยเงื่อนไข delay 300ms ได้ completion ต่ำสุด (15/20)
- **รายงานเป็นผลเชิงสำรวจ (exploratory) เท่านั้น ไม่ใช่ headline** เพราะ: (1) CI ทับซ้อนกันเกือบทั้งหมด (2) การทดลองควบคุมในภายหลังที่ sample size เท่ากันได้ลำดับผลตรงข้าม (3) การออกแบบเปลี่ยนสองปัจจัยพร้อมกัน (task ยากขึ้น + reviewer เข้มขึ้น) ทำให้แยกสาเหตุไม่ได้ (4) กลไกที่คาดไว้ (timeout สะสมความเสียหายข้ามรอบ) ไม่ปรากฏในข้อมูลจริง (mean timeout ต่อ trial = 0.05 เท่านั้น)

## Tier 3 — ความน่าเชื่อถือของตัวประเมินผล (Evaluator Validity)

- **เปลี่ยนตัวตัดสิน (judge)**: ให้ LLM สองตัว (`qwen3:8b`, `llama3.1:8b`) ให้คะแนนชุดเดียวกัน 200 trials พบ **ความสอดคล้องใกล้ศูนย์** (Cohen's κ = 0.00, weighted κ = 0.010, Pearson r = 0.11) — `llama3.1:8b` ให้คะแนนเต็มแก่ 198/200 trials รวมถึง 18 trial ที่ rubric บอกว่าล้มเหลวชัดเจน
- **เปลี่ยนโมเดล agent**: rerun แกนหลัก 840 trials ด้วย `llama3.1:8b` แทน `qwen3:8b` — completion ใกล้เคียงเดิม แต่ **rubric pass rate ต่างกันมากใน 2 จาก 4 งาน** (data analysis 210/210 → 43/210, χ² p = 1.58×10⁻⁶¹; research summary 139/210 → 19/210, χ² p = 4.18×10⁻³³)
- **ข้อสรุป**: ทั้งสองผลไม่สามารถบอกได้ว่า evaluator ตัวไหน "ถูกต้อง" (ไม่มี human label อ้างอิง) — สิ่งที่ยืนยันได้แน่นอนคือ **ข้อสรุปเรื่องคุณภาพงานในระบบนี้ขึ้นอยู่กับตัวประเมินผลอย่างมาก** เป็นข้อควรระวังเชิงระเบียบวิธี ไม่ใช่ contribution หลักของงาน

---

## Tier 4 — การทำซ้ำ (Replication)

**Temporal replication** (รัน 1,544 trials เดิมซ้ำในช่วงเวลาที่ต่างออกไป):
- **รูปแบบการกระจุกตัวของ degradation ที่ loss สูงสุดเกิดซ้ำ** — completion รวม 1,514/1,544 เทียบ 1,500/1,544 (p = 0.126, ไม่ต่างอย่างมีนัยสำคัญ, risk difference +0.9pp, 95% CI −0.2 ถึง +2.0 — ช่วงแคบ บ่งชี้ว่าการเปลี่ยนแปลงเชิงระบบขนาดใหญ่ไม่น่าเกิด)
- ที่ 75% loss โดยเฉพาะ: 16/20 เทียบ 13/20 (p = 0.480, CI −12.4 ถึง +39.8 — กว้าง จึงไม่ควรสรุปว่า "ไม่มีการเปลี่ยนแปลง")
- **สถานะปัจจุบัน**: ตัวเลข 75%-loss ทั้งสอง run นี้ยังถูกต้องสำหรับช่วงเวลาที่วัด แต่ไม่ควรอ้างเป็นเงื่อนไขเป้าหมายที่เสถียรข้ามเวลา เพราะ Tier 8/9 พบว่าช่วงเวลาหลังจุดวิกฤตเปลี่ยนไปที่ 80%

**Cross-model replication** (rerun แกนหลักด้วย `llama3.1:8b`):
- completion ใกล้เคียงกัน (16/20 เทียบ 19/20 ที่ 75% loss) แต่ **rubric pass rate ต่างกันมาก** ในสองงาน (ดู Tier 3) — เป็นปัญหาเรื่อง evaluator ไม่ใช่ความสามารถของโมเดล

## Tier 5 — มาตรการบรรเทาผลกระทบ (Mitigation)

การทดลอง 660 trials (220 ต่อเงื่อนไข: control, condition-aware timeout scaling, context caching) ที่ configured loss ทุกระดับ:

- **Condition-aware timeout scaling**: completion ที่ 75% loss = **14/20 (control) เทียบ 20/20 (timeout scaling)** (two-sided Fisher's exact p = 0.0202, Holm-adjusted p = 0.0404; risk difference +30.0pp, 95% CI +7.7 ถึง +51.9) แลกกับเวลาที่เพิ่มขึ้น (+37% ที่เงื่อนไขนั้น, +12.4% โดยรวม)
- **Context caching**: 16/20 เทียบ control 14/20 — **ไม่มีนัยสำคัญทางสถิติ** (p = 0.716) และพบว่า mitigation นี้มี design defect (ไม่ได้ตัดการเรียก Planner ตัวแรกออกอย่างที่ตั้งใจ เพราะ Planner ไม่เรียก model บน single-pass path อยู่แล้ว)
- **caveat ที่ต้องติดไปกับผลนี้เสมอ 6 ข้อ**: (1) สูตร timeout ใช้พารามิเตอร์ที่รู้อยู่แล้ว ไม่ใช่ประมาณจาก path จริง (2) ไม่เคยเทียบกับ fixed timeout ที่ยาวเท่ากันที่ 75% loss โดยเฉพาะ (3) ไม่เคยถูก replicate อิสระ (4) เงื่อนไขรันเป็น block ต่อเนื่อง ไม่สลับกัน (5) ผลจำเพาะกับช่วงเวลาที่วัด — ช่วงเวลาหลังไม่พบ degradation ที่ 75% loss อีกต่อไป และการเทียบใหม่ที่จุดวิกฤต 80% ของช่วงเวลานั้นได้ผลลัพธ์กลับด้าน (ดู Tier 9) (6) contrast แบบไม่มีมาตรการเลยของโครงการเองก็ให้ผลต่างกันในขนาดใกล้เคียงกัน (15-20pp โดยไม่มีการเปลี่ยนแปลง code path ใดๆ — ดู Tier 6)

## Tier 6 — มาตรการบรรเทาผลกระทบ × Multi-round เข้มงวด (120 trials)

- **ไม่มีการเปรียบเทียบใดผ่านนัยสำคัญทางสถิติ** (Fisher's exact p > 0.05 ทั้ง 6 การเปรียบเทียบ)
- **การตรวจสอบ falsification ล้มเหลว — ข้อค้นพบสำคัญที่สุดของ Tier นี้**: ที่ scenario ไม่มี impairment เลย สูตร timeout-scaling คำนวณค่าเพิ่มเป็นศูนย์เสมอ (code path เดียวกับ control ทุกประการใน 20/20 trials) และ caching branch เกิดเพียง 1/20 trials — แต่ completion ต่างกันถึง **15-20 percentage point ระหว่าง arm ที่ไม่มีมาตรการทำงานอยู่เลย** (14/20, 17/20, 18/20) นี่คือหลักฐานว่า **ความผันแปรระหว่าง block ในระดับนี้เกิดขึ้นได้เองแม้ไม่มีการรักษาใดๆ ทำงาน** — ทำให้ผลต่างขนาดใกล้เคียงกันใน Tier 5 ต้องถูกตีความอย่างระมัดระวัง

## Tier 7 — ความพยายามปิดช่องว่าง 3 จุด (ผลลัพธ์: 2 โมฆะ, 1 สำเร็จบางส่วน)

| ส่วน | เป้าหมาย | ผลลัพธ์ |
|---|---|---|
| **7A** — fixed-long-timeout arm | เทียบ timeout คงที่กับ adaptive scaling ที่ 65/70/75% loss | **รันสำเร็จ (60/60 trials) แต่ใช้ไม่ได้** — พบ logging defect ที่ทำให้ retry ถูกข้ามไปเมื่อเกิด error ทำให้จำนวนความล้มเหลว (13/20 ที่ 75%) ไม่ใช่การวัดที่ตั้งใจ ช่องว่างนี้ยังเปิดอยู่ที่ระดับ loss เดิม |
| **7B** — bidirectional shaping | ทดสอบว่า bandwidth/delay non-detection คงอยู่หรือไม่เมื่อ shape ทั้งสองทิศทาง | **รันสำเร็จ (80/80 trials) แต่ใช้ไม่ได้** — falsification check ล้มเหลวเอง (control ที่ไม่มี impairment ได้ 14/20 = 70% แทนที่จะเป็น ~100%) |
| **7C** — agent attribution ใน log | บันทึกว่า timeout เกิดกับ agent ไหนโดยตรง | **สำเร็จบางส่วน** — การกู้คืนย้อนหลัง (Worker 19, Reviewer 18, Planner 1 จาก 38 เหตุการณ์) ใช้ได้ แต่ความสามารถบันทึกใหม่แบบ real-time มี defect เดียวกับ 7A |

ทั้งช่องว่างของ 7A และ 7B ถูกปิดสำเร็จในภายหลังโดย Tier 9 (สำหรับ 7A ที่ระดับ 80%) และ Tier 8 item 4 (สำหรับ 7B)

## Tier 8 — ปิดช่องว่างของ scope (1,020 trials + diagnostic 80 trials)

5 การวัดอิสระ ปิดหรือชี้แจงข้อจำกัดที่เปิดค้างไว้ก่อนหน้า:

1. **Achieved-path measurement**: วัดค่าจริงที่เกิดขึ้นบน path เทียบกับค่าที่ config — delay 3,000ms configured ได้ achieved mean 3,002.8ms; loss 75% configured ได้ achieved mean 74.7%/median 75.1% — **ปิดช่องว่าง configured-vs-achieved สำหรับ delay และ loss เท่านั้น ที่จุดที่ทดสอบ ไม่ปิดสำหรับ bandwidth** (payload ของ probe เล็กเกินกว่าจะสะท้อน token-bucket burst allowance)
2. **Fixed-long-timeout ที่ 65/70/75% loss**: ทั้ง 3 arm (control, adaptive, fixed) ได้ 20/20 ทุกจุด (180/180) — **ไม่สามารถแก้ปัญหาเดิมได้ เพราะ control เองก็ไม่แสดง degradation ในสภาพแวดล้อมปัจจุบันแล้ว** (ดูข้อ 6)
3. **Mitigation comparison แบบสุ่มลำดับ (660 trials)**: completion 658/660 (99.7%) ทุกเงื่อนไขทุกระดับ loss รวมถึง 75% — เหตุผลเดียวกับข้อ 2 คือสภาพแวดล้อมเปลี่ยนไปแล้ว การสุ่มลำดับเองทำงานถูกต้อง (ยืนยันด้วย manifest) แต่ตอบคำถามเดิมไม่ได้
4. **Bidirectional (egress+ingress) shaping**: baseline=20/20, bandwidth 50kbit/s=20/20, delay 1000ms=20/20, **loss 75%=0/20** — ผ่านทั้ง 2 falsification check ที่กำหนดไว้ **ปิดข้อจำกัด egress-only สำหรับ bandwidth และ delay เฉพาะที่จุดทดสอบทั้งสองนี้เท่านั้น** ไม่ใช่ทั้งโครงการ (ทุกผลอื่นในโครงการยังเป็น egress-only)
5. **Matched control สำหรับ jitter delay-floor**: 50ms delay + 0ms jitter ได้ 20/20 เท่ากับ zero level เดิม (20/20) — **ปิดข้อจำกัดนี้สำหรับ completion เท่านั้น ไม่ปิดสำหรับ elapsed time หรือตัวชี้วัดรองอื่นๆ**
6. **ข้อค้นพบใหม่ที่ไม่ได้วางแผนไว้ล่วงหน้า (current-environment finding)**: 75% configured loss **ไม่ทำให้ completion ตกอีกต่อไป**ในช่วงเวลาการวัดหลัง (ใกล้ ceiling) ตรวจสอบด้วย controlled ablation (ปิด thinking-mode) ไม่พบความต่าง — สาเหตุคือ **ความเร็วของสภาพแวดล้อม serving เปลี่ยนไปราว 2 เท่า** (median elapsed time ของ trial ที่สำเร็จตั้งแต่ครั้งแรกที่ 75% loss: 248 วินาที → 127 วินาที) ไม่ใช่การเปลี่ยนแปลงกลไก reasoning ของโมเดล **ผลลัพธ์เดิมที่ 75% loss ไม่ถูกแก้ไข** — ยังคงถูกต้องสำหรับช่วงเวลาที่วัด แต่ห้ามอ้างเป็นเงื่อนไขเป้าหมายที่เสถียรข้ามเวลาโดยไม่เปิดเผยข้อจำกัดนี้

## Tier 9 — ปรับหาจุดวิกฤตใหม่ (120 trials)

**การสำรวจหาจุดวิกฤต (Exploratory scan, n=12/ระดับ):**

| Configured loss | Completion |
|---|---|
| 80% | 3/12 (25%) |
| 85% | 1/12 (8%) |
| 90% | 0/12 (0%) |
| 95% | 0/12 (0%) |
| 99% | 0/12 (0%) |

**80% คือจุดวิกฤตเดียวที่ถูกนำไปเปรียบเทียบต่อ** (ไม่ใช่ "ช่วง 80-85%" — 85% เป็นเพียงจุดหนึ่งใน scan)

**การเปรียบเทียบเต็มรูปแบบที่ 80% loss (n=20/arm):**

| เงื่อนไข | Completion | เทียบ control |
|---|---|---|
| control | 5/20 (25%) | — |
| adaptive_timeout | 1/20 (5%) | p = 0.182 (ไม่มีนัยสำคัญ) |
| fixed_long_timeout | 13/20 (65%) | **p = 0.0248** (มีนัยสำคัญ) |
| adaptive vs. fixed | — | **p < 0.001** |

- **fixed timeout ที่ยาวคงที่ให้ผลดีกว่า adaptive timeout scaling อย่างมีนัยสำคัญ ที่จุดวิกฤตของสภาพแวดล้อมปัจจุบัน — เป็นลำดับผลลัพธ์ที่ตรงข้ามกับ Tier 5 เดิม**
- สาเหตุส่วนหนึ่ง: ที่ 80% loss ความล้มเหลวจำนวนมากเป็น connection-establishment failure (`ConnectionError`) ไม่ใช่ call ที่ช้าเกินจน timeout — `ConnectionError` เกิด 13 ครั้งใน control, 20 ครั้งใน adaptive_timeout (มากที่สุด), 6 ครั้งใน fixed_long_timeout; ส่วน `timeout` event (นับแยกต่างหาก) เกิด 36 ครั้งใน control, 39 ครั้งใน adaptive_timeout, 24 ครั้งใน fixed_long_timeout — เป็นรูปแบบความล้มเหลวที่ timeout ค่าไหนก็แก้ไม่ได้
- **ข้อจำกัดบังคับที่ต้องติดไปด้วยเสมอ**: ทั้ง 3 arm รันเป็น 3 block ต่อเนื่องกัน ไม่ได้สลับลำดับ (ตลอดราว 5 ชั่วโมง) — เป็นข้อจำกัดแบบเดียวกับ Tier 5 เดิม นอกจากนี้ยังมี **บั๊กใน client wiring** ของ Tier นี้เอง (custom `model_client_cls` ไม่รับค่า `timeout` ที่ตั้งใจส่งมาจาก `llm_config` — ยืนยันทั้งจากโค้ดและจากข้อความ error ดิบทุกอันที่มี `timeout=120` ฝังอยู่) ทำให้ทั้ง 3 arm ใช้ timeout จริงราว 120 วินาทีเท่ากันหมด ไม่ใช่ค่าที่ตั้งใจให้ต่างกัน (adaptive/fixed ควรได้ 360 วินาที) — ผลต่าง completion ระหว่าง arm ยังเป็นของจริงและมีนัยสำคัญทางสถิติ แต่กลไกที่แท้จริงที่ทำให้เกิดผลต่างนี้ยังเป็นคำถามเปิด ไม่ใช่ผลจากงบเวลาที่ต่างกัน (ดู `NetImpact_22_...` §2)
- **ไม่ได้เขียนทับผลของ Tier 5**: ผล 75%-loss เดิมยังถูกต้องสำหรับช่วงเวลาที่วัด นี่คือการเปรียบเทียบ completion rate ครั้งแรกของโครงการระหว่าง fixed timeout กับ adaptive timeout ที่จุดวิกฤตของสภาพแวดล้อมปัจจุบัน — เป็นหลักฐานล่าสุดที่ดีที่สุด ไม่ใช่ตัวแทนที่มาแทนผลเดิม

## สรุปภาพรวมทั้งโครงการ

**สามผลลัพธ์หลักที่จะนำเสนอเป็น contribution ของงานวิจัย:**

1. **การสำรวจอย่างเป็นระบบ 4 พารามิเตอร์ของ egress impairment** (delay, packet loss, jitter, bandwidth) บน model-serving path ของ AutoGen workflow 3 บทบาท — "เป็นระบบ" แต่ไม่ใช่ "ควบคุมสมบูรณ์" เพราะลำดับ trial ไม่เคยสุ่ม แกน jitter ไม่มี matched zero-control ที่สมบูรณ์ และ achieved-path measurement ปิดได้เฉพาะ delay/loss ที่จุดทดสอบเท่านั้น
2. **Degradation region ที่ชัดเจนของ packet loss** อยู่ที่ 70-75% (ในช่วงเวลาที่วัดครั้งแรก) ซึ่งเกิดซ้ำในการ rerun อิสระเต็มรูปแบบ ส่วน delay, jitter, bandwidth ไม่พบ degradation ชัดเจนแม้ทดสอบถึงจุดสุดขั้ว — พร้อมเปิดเผยว่าผลนี้จำเพาะกับช่วงเวลาที่วัด (ช่วงเวลาหลังจุดวิกฤตย้ายไปที่ 80%)
3. **ผลต่างระหว่าง block ของมาตรการ condition-aware timeout scaling** ที่สังเกตได้ พร้อมต้นทุนด้านเวลาที่เปิดเผยครบ, p-value ที่ปรับ Holm แล้ว, และ scope condition ทั้ง 6 ข้อ (รวมถึงการค้นพบว่าที่จุดวิกฤตของช่วงเวลาการวัดหลัง ผลลัพธ์กลับด้าน — fixed timeout ดีกว่า adaptive)

**สิ่งที่ไม่ใช่ contribution หลักแต่ต้องเปิดเผย**: ความไวของผลลัพธ์ต่อตัวประเมินผล (evaluator) เป็นข้อควรระวังเชิงวิธีวิจัย ไม่ใช่ headline; ผลของโหมด multi-round เข้มงวดเป็นเชิงสำรวจเท่านั้น (ทั้งจากช่วง CI ที่ทับซ้อนกันมาก และจากการควบคุมที่ไม่ reproduce); การเปรียบเทียบมาตรการบรรเทาในโหมด multi-round ล้มเหลวในการ falsification check ของตัวเอง

**สถานะที่ยังเปิดอยู่ (ยังไม่ปิด แม้จะพยายามหลายครั้ง):**
- Achieved-path measurement ของแกน bandwidth (probe ที่ใช้เล็กเกินไป)
- การเทียบ fixed timeout กับ adaptive timeout **ที่ระดับ 75% loss โดยเฉพาะ** (ความพยายามครั้งแรกใช้ไม่ได้เพราะ logging defect; ครั้งที่สองสภาพแวดล้อมเปลี่ยนจนไม่มี degradation ให้เทียบ) — มีเพียงการเทียบที่ระดับ 80% ของสภาพแวดล้อมช่วงหลังเท่านั้นที่ใช้ได้จริง
- Elapsed-time confound ของ jitter delay-floor (ปิดแล้วเฉพาะ completion)
- ขนาดของความผันแปรระหว่าง block แบบไม่มีมาตรการ (15-20pp) หมายความว่าผลต่างในระดับใกล้เคียงกันควรถูกตีความอย่างระมัดระวังทุกครั้ง

**ข้อสรุปที่สำคัญที่สุดของโครงการทั้งหมด**: ทุกผลลัพธ์เชิงปริมาณต้องระบุ "ช่วงเวลาที่วัด" กำกับไว้เสมอ เพราะพบโดยตรงว่าสภาพแวดล้อมการรัน (ความเร็วของ inference server) เปลี่ยนแปลงได้เองระหว่างช่วงเวลาต่างๆ ของโครงการ และเปลี่ยนทั้งตำแหน่งของจุดวิกฤต (75%→80%) และทิศทางของผลการเปรียบเทียบมาตรการบรรเทา (adaptive ดีกว่า → fixed ดีกว่า) — นี่คือข้อจำกัดเชิงวิธีวิจัยที่ต้องเดินทางไปกับทุกการอ้างตัวเลขในเปเปอร์
